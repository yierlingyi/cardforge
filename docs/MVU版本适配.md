# MVU 版本适配说明

> 结论先行：**`mvu`、`mvubeta`、`mvuzod` 三者不是同一套接口的不同叫法，也不保证字段完全一致。**
> CardForge 采取「先识别、再适配、无法确认就明说」的策略：能静态确定的结构完整解析；
> 依赖运行时 JavaScript 的部分显式标注为「动态/未知约束」，不伪装成已理解。

---

## 1. 三个版本的关系与识别

### 1.1 识别信号（加权打分）

| 信号 | 归属 | 权重 | 证据等级 |
| --- | --- | --- | --- |
| `registerVariableSchema(` | mvuzod | 6 | 惯例（Zod 版注册 Schema 的调用） |
| `z.object(` | mvuzod | 4 | 惯例 |
| `z.string() / z.number() / z.array() / z.enum() …` | mvuzod | 2 | 惯例 |
| 直接 `import 'zod'` | mvuzod | 2 | 惯例 |
| 脚本/条目提及 `MagVarUpdate` | mvu | 3 | 惯例 |
| `MVU Beta` 字样 | mvubeta | 4 | 待验证（可能是分支命名，而非稳定标识） |
| `stat_data` 引用 | mvu / mvuzod | 2–3 | 惯例 |
| `display_data` / `delta_data` 引用 | mvu | 1 | 惯例 |
| `Mvu.` 接口调用 | mvu | 2 | 惯例 |
| `_.set/_.add/_.insert/_.remove…` | mvu | 1 | 惯例 |
| `变量更新规则` / `JSON Patch` 说明 | mvu | 1 | 惯例 |
| 世界书条目 `[InitVar]` / `初始化变量` | mvu | 3 | 惯例（命名不统一，属启发式） |
| 正文含 `stat_data` | mvu | 2 | 惯例 |
| 正文提及 `Zod` / `$schema` | mvuzod | 1–2 | 惯例 |

**置信度**：

- `high`：最佳得分 ≥ 8 且 ≥ 次高 1.5 倍；或 `mvuzod` 出现明确 `registerVariableSchema`（因 mvuzod 是 mvu 的超集，基础版信号密集不影响判定）。
- `medium`：最佳 ≥ 4 且高于次高。
- `low`：最佳 < 2（判为 `unknown`，页面降级为「可手动导入变量」）。

UI 会展示每条证据（来源脚本/条目 + 说明 + 权重），用户可自行判断识别是否合理。

### 1.2 版本对照表

| 维度 | mvu | mvubeta | mvuzod | 证据等级 |
| --- | --- | --- | --- | --- |
| 核心变量 | `stat_data` | 同左（推定） | 同左 | 惯例 |
| 展示变量 | `display_data` | 同左（推定） | 同左（推定） | 待验证 |
| 增量变量 | `delta_data` | 同左（推定） | 同左（推定） | 待验证 |
| 变量初始化 | 世界书条目（`[InitVar]` 等），内容为 YAML/JSON | 同左（推定） | 同左 + Schema 注册 | 惯例 / 待验证 |
| 更新协议 | JSON Patch 数组、`_.xxx()` 调用 | 推定一致 | 推定一致 + Zod 校验 | 惯例 / 待验证 |
| Schema | 无内建 Zod | 待验证 | `registerVariableSchema` | 惯例 |
| 楼层变量 | 消息级变量 | 推定一致 | 推定一致 | 待验证 |
| 与脚本交互 | `Mvu` 全局、事件常量 | 待验证 | 同左 + Schema API | 待验证 |

> **说明**：本表把「推定一致」明确写出来，是因为这些结构在真实卡片中高度相似，但本次未在
> 三个版本的运行时中逐项对照。CardForge 因此不依赖版本差异做严格分支，而是：
> 1）识别版本并展示置信度；2）用统一的容错读取器提取变量与 Schema；
> 3）把无法静态判定的部分标为动态；4）允许用户手动导入变量快照覆盖解析结果。

## 2. 变量数据的来源与优先级

```
用户导入的变量快照（最高）
      ↓ 无
世界书初始化条目（[InitVar] / 变量初始化 / 含 stat_data: 前缀）
      ↓ 解析失败或无
脚本中的静态定义（仅作为提示，不执行）
      ↓ 无
empty（页面提示导入）
```

**初始化条目识别**（`findInitVarEntry`）：

1. 备注完全匹配 `[InitVar]` / `initvar` / `变量初始化` / `初始化变量` / `初始变量`（忽略大小写与方括号）。
2. 备注或正文前 200 字包含上述关键词。
3. 正文以 `stat_data:` 或 `变量:` 开头，且备注含「变量/variable」。

**内容解析**（`parseInitVar`）：

- 以 `{` 开头 → JSON；否则走 YAML 子集解析器。
- 若顶层只有 `stat_data` / `variables` / `initvar` 一个键，自动剥壳并标注。

### YAML 子集支持范围

| 语法 | 支持 | 说明 |
| --- | --- | --- |
| 嵌套映射、缩进 | ✅ | 空格缩进；Tab 按 2 空格计 |
| 序列 `- item`、序列内映射 | ✅ | 含续行键 |
| 引号字符串、转义 | ✅ | 单/双引号 |
| 数字 / 布尔 / null / `~` | ✅ | 含 `0x` 十六进制 |
| 行内数组 `[a,b]` / 对象 `{a:1}` | ✅ | 宽松解析 |
| 块标量 `\|` / `>` | ✅ | 基础实现（不含折行细节） |
| 注释、`---` | ✅ | 忽略 |
| 锚点 `&` / 别名 `*` | ⚠️ | 告警并按字符串处理 |
| 多文档合并、复杂标签 | ❌ | 明确提示不支持 |

> 解析器是「为 MVU 初始化变量服务的最小实现」，不是通用 YAML 引擎。解析失败会给出错误位置，
> 不会静默产出半截数据。

## 3. Zod Schema 静态解析

### 3.1 支持的构造器

| Zod 表达式 | 解析结果 | 备注 |
| --- | --- | --- |
| `z.string/number/bigint/boolean/null/any/unknown/date` | 类型 | — |
| `z.literal(x)` | 类型 + 默认值 | — |
| `z.enum([...])` | enum + 可选值约束 | — |
| `z.array(z.object({...}))` | 数组 + 元素字段（路径 `x[]`） | 支持嵌套 |
| `z.object({...})` | 对象 + 子字段 | 支持 4 层以上嵌套 |
| `z.union([...])` | 类型并集 | 对象分支会展开字段 |
| `z.tuple([...])` | 定长元组 | 不展开元素 |
| `z.record(...)` | object + 动态键标记 | 字段不可枚举 |
| `z.coerce.number()` | number + 转换标注 | — |

### 3.2 支持的链式约束

`.optional()` → 非必填；`.nullable()` → 类型加 `| null`；`.default(v)` → 默认值 + 非必填；
`.min/.max/.length` → 范围约束（数值/字符串/数组分别校验）；`.int/.positive/.nonnegative`；
`.regex(...)`；`.describe(...)`；根对象 `.partial()`。

### 3.3 明确标记为「动态/未知」的情况

| 写法 | 处理 |
| --- | --- |
| `.transform()` / `.refine()` / `.superRefine()` / `.catch()` | 记录「运行时逻辑，静态不可判定」 |
| `z.object(someVar)`（非字面量） | 记录「字段来自变量或函数调用」 |
| 展开语法 `...BaseSchema` | 记录「该部分无法静态展开」 |
| 计算属性名、函数返回 Schema | 同上 |
| `z.custom()` / `z.preprocess()` | 类型标为 any + 动态标记 |

UI 的「Schema」页会把不可判定项单独列出；不会显示为「已完整理解」。

### 3.4 数据与 Schema 的关联校验

- 类型不匹配 → error。
- 数值/长度越界 → error。
- 枚举值不在范围 → warning。
- 必填但数据缺失 → warning（默认值存在时不报）。
- 「只在数据中」「只在 Schema 中」的路径分别列出。

> 这些结果是**静态推断级别**的提示，最终以运行时 Zod 校验为准；UI 每次都会带上这句限定。

## 4. 变量更新与 JSON Patch

### 4.1 支持的输入格式

1. 标准 JSON Patch 数组：

```json
[{ "op": "replace", "path": "/角色/好感度", "value": 30 }]
```

2. `_.xxx()` 调用风格：

```js
_.set('角色.好感度', 30);
_.remove('世界.天气');
```

点路径会转换为 JSON Pointer（`角色.好感度` → `/角色/好感度`）。

### 4.2 支持的操作

`add`、`remove`、`replace`、`move`、`copy`、`test`（`test` 失败会中断并报告第几个操作）。

### 4.3 已知语义差异（必须知道）

- `_.add` 在运行时可能表示**数值累加**，而补丁语义是「新增/覆盖」。CardForge 按字面值写入，并在结果中提示。
- 运行时的变量更新可能受「楼层」「消息 ID」「swipe」影响；编辑器的 Patch 测试只针对单一变量树。
- 更新失败原因（路径不存在、数组越界、test 不符）会精确定位到操作序号。

## 5. 多楼层变量

导入格式：

```json
[{ "index": 0, "stat_data": { ... } }, ...]
```

或 `{ "floors": [ ... ] }`，或纯对象数组（自动编号）。

支持：

- 楼层列表 + 标签；
- 任意两楼层差异对比；
- 当前变量与任一楼层对比；
- 每个楼层与当前的补丁数量。

**限制**：不模拟变量随消息的实时演化，也不解析聊天记录文件（需要 SillyTavern 的 chat JSONL 结构，且变量在消息 `variables` 字段中）。用户需要自行导出/整理变量快照。

## 6. 与运行时核对的方法（建议流程）

若你的卡片依赖 MVU 的精确行为，建议在真实环境中做一次对照：

1. 在 SillyTavern 打开卡片，触发几轮对话。
2. 在浏览器控制台执行（示例思路，具体 API 以安装版本为准）：

```js
// 查看当前消息变量
const ctx = SillyTavern.getContext();
console.log(ctx.chat[ctx.chat.length - 1]?.variables);
```

3. 把 `stat_data` 复制到 CardForge「MVU → 导入变量」，对比字段是否一致。
4. 用「Patch 测试」复现一次运行时更新，检查差异。
5. 若发现 CardForge 的字段名/结构与实际不同，请以实际运行结果为准，并可在 `src/core/mvu.ts` 的适配层补充映射。

> 我们没有把「某版本的精确字段」写死为事实，是因为这些扩展仍在演进，且不同分支的打包方式不同。
> 宁可显示「待验证」，也不给出看似确定但可能是错的结论。

## 7. 降级策略

| 情况 | 行为 |
| --- | --- |
| 未识别到 MVU 特征 | 页面可用，变量为空，提示手动导入 |
| 初始化条目解析失败 | 保留错误信息，变量为空，不猜测 |
| Schema 无法定位 | 使用数据推断结构（明确标注「来自数据推断」） |
| 变量数据不是对象 | 提示类型错误，不强行包裹 |
| 导入的楼层格式不符 | 报错并给出期望格式 |
